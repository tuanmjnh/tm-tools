# TMCut v3 --- Asset Center, Template Studio, AI Editor & AutoCut AI Roadmap

-   **Document type:** Technical implementation roadmap for AI coding
    agents
-   **Version:** 2.0
-   **Date:** 2026-10-18
-   **Status:** Proposed; repository audit required before
    implementation
-   **Primary stack:** Electron, Vite, Vue 3, Pinia, existing
    FFmpeg/FFprobe task infrastructure
-   **Long-term direction:** Shared TMCut Core, separate Preview and
    Render Engines, optional Web Runtime, provider adapters

> This document extends and supersedes the previous Asset Center-only
> roadmap. It combines on-demand assets, user/AI-created templates,
> conversational AI editing, fully automated AutoCut, and configurable
> AI/media-generation provider connections.

------------------------------------------------------------------------

## 1. Product vision

TMCut should become a modular video-editing platform with four
cooperating subsystems:

1.  **Asset Center** --- browse, preview, download, update, and manage
    optional resources on demand.
2.  **Template Studio** --- create, edit, validate, save, share, import,
    and reuse templates created by the user or generated by AI.
3.  **AI Editor** --- an assistant inside the normal editor that can
    create a complete editable project/timeline, then iteratively modify
    it through validated edit operations.
4.  **AutoCut AI** --- a guided, high-automation workflow: choose source
    media, describe the intended result, set optional preferences,
    review the generated plan, then render and export with minimal
    manual timeline work.

A fifth cross-cutting subsystem, **AI Provider Hub**, routes requests to
configured language, vision, image, audio, and video-generation
providers using capability-aware adapters.

The system must remain useful if a provider is unavailable. AI-generated
plans must be inspectable and editable. Rendering must remain
deterministic to the extent supported by the selected backend. The
existing FFmpeg renderer remains the baseline while other backends may
be added later.

### Product principle

**AI proposes and orchestrates edits; TMCut Core validates and applies
edits; render backends execute the final timeline.** AI providers must
not directly manipulate arbitrary files, run shell commands, or invoke
FFmpeg with unrestricted commands.

## 2. Repository audit is mandatory

Before implementation, the coding agent must inspect the real repository
and report:

-   Current monorepo/package structure and entry points.
-   Existing project model, Timeline DSL, media/asset references,
    serialization, autosave, and migration strategy.
-   Current FFmpeg/FFprobe task manager, render compiler, export modal,
    progress/cancellation events, and error handling.
-   Existing preview player, timeline, selection model, Inspector Panel,
    keyframe system, and effect/transition support.
-   Existing AI/AutoCut code, prompts, EDL format, model settings, and
    provider configuration.
-   Existing Electron IPC/preload conventions and safe filesystem
    access.
-   Existing backend/API, database, object storage, authentication,
    settings, and secrets handling.
-   Existing test, lint, type-check, and build commands.

Produce a mapping table of **existing capability → reusable module → gap
→ proposed change**. Do not create duplicate abstractions when an
equivalent already exists. Do not perform a large refactor before
reporting the audit and migration plan.

### Architectural boundaries

-   Core must not import Vue, Electron, Node.js, a provider SDK, or
    FFmpeg-specific command syntax.
-   Provider adapters normalize external API differences into internal
    typed results.
-   Asset packages and AI-generated media are inputs to the project;
    they are not executable code.
-   The AI Orchestrator emits structured plans and calls approved tools
    only.
-   Core validates every edit operation before changing a project.
-   Render backends compile a validated render graph; the AI model must
    not generate arbitrary shell commands.
-   Keep provider credentials out of the renderer and out of project
    files.
-   Every expensive generation task must have an explicit user-visible
    cost/usage policy, cancellation state, and failure state.
-   Optional services must be replaceable without changing the project
    format.

## 4. Core domain concepts

Keep these separate:

1.  **Asset definition:** reusable media or effect package in the
    catalog.
2.  **Installed asset:** a verified local version of a package.
3.  **Template definition:** reusable project structure and
    parameterized layout.
4.  **Project:** the user's editable working document.
5.  **Timeline instance:** a specific clip/effect/transition/text/audio
    object in a project.
6.  **AI Edit Plan:** a proposed sequence of structured operations.
7.  **AutoCut Job:** an orchestrated workflow with input analysis, plan
    generation, media acquisition/generation, validation, and render
    stages.
8.  **Provider connection:** a configuration for a service, endpoint,
    credential reference, and supported capabilities.
9.  **Generated media:** an image/audio/video asset produced by a
    provider and imported into the project or Asset Center according to
    the user's choice and rights.

A template must not be a rendered MP4 masquerading as an editable
template. It should preserve editable tracks, placeholders, timings,
text, effects, transitions, and asset references wherever supported.

# PART A --- ON-DEMAND ASSET CENTER

## 5. Asset Center goals

The installer should contain the editor, essential runtime components,
and only a small starter set. The optional catalog is downloaded when
requested.

Supported categories may include:

-   Effects
-   Filters and LUTs
-   Transitions
-   Stickers and overlays
-   Text/title presets
-   Fonts
-   Music and sound effects
-   Template packs
-   Image/video overlays
-   User-imported resources

### Asset lifecycle

``` text
Catalog item
 -> Details / preview
 -> Check rights + compatibility + entitlement
 -> User requests download
 -> Queue download
 -> Download to temporary storage
 -> Validate size, hash, manifest and archive paths
 -> Install atomically
 -> Register installed version
 -> Apply to project
 -> Update / disable / uninstall safely
```

### Requirements

-   Search, categories, tags, filters, sorting, pagination, favorites.
-   Preview media distinct from the full package.
-   Download queue with progress, cancellation, retry, bounded backoff,
    and restart recovery.
-   SHA-256 verification against a trusted manifest.
-   Safe archive extraction, path-traversal rejection, file-count and
    decompressed-size limits.
-   Atomic install; never mark a package installed before validation
    succeeds.
-   Offline use for already installed assets.
-   Storage controls and cleanup that protect assets used by open/pinned
    projects.
-   Asset IDs and versions in project data; no hardcoded absolute paths.
-   Missing/withdrawn asset recovery choices when opening projects.
-   Electron storage in the app's user-data directory, never inside
    `app.asar`.
-   Future web runtime may use IndexedDB/OPFS/Cache Storage where
    supported.

### License registry

Track source, creator, license name/URL, attribution, modification
rights, commercial use in exported videos, redistribution inside the
app, standalone file distribution, territories/expiry where applicable,
proof, review status, reviewer, and review date.

Unknown or unreviewed rights must not be represented as approved. "Free
to use in a video" is not equivalent to permission to rehost or
redistribute the raw file. Music may involve separate rights in the
recording and composition. Do not scrape or repackage proprietary CapCut
resources without authorization.

# PART B --- TEMPLATE STUDIO

## 6. Template product goals

Template Studio must support:

-   Create a template manually from the current project.
-   Save a selection of tracks/clips as a reusable template where
    supported.
-   Start from a built-in or downloaded template.
-   Generate a template from a natural-language description using AI.
-   Convert a valid AI-generated project into a template.
-   Import/export a versioned TMCut template package.
-   Edit template metadata, placeholders, timing rules, and supported
    parameters.
-   Preview the template with sample media.
-   Apply a template to a new project or selected media.
-   Replace placeholder media while preserving layout and timing where
    possible.
-   Save private templates locally; optional account sync or marketplace
    is a later phase.
-   Version templates and migrate old schemas safely.

### 6.1 Template types

Use explicit types rather than a single generic "template" flag:

-   `project-template`: full editable project skeleton.
-   `sequence-template`: reusable timeline section.
-   `title-template`: editable text and animation preset.
-   `social-video-template`: a project layout designed for a target
    aspect ratio/platform.
-   `audio-template`: reusable music/SFX structure, where licensing
    allows.
-   `effect-preset`: parameter values for an effect.
-   `transition-preset`: parameter values for a transition.
-   `autocut-profile`: an editing policy/profile used by AutoCut, not a
    rendered video.
-   `ai-workflow-template`: a saved prompt, constraints, and approved
    operation recipe; never executable arbitrary code.

### 6.2 Template schema

Fit this to the existing project format; the following is illustrative:

``` ts
interface TmcutTemplate {
  schemaVersion: number
  id: string
  version: string
  title: string
  description?: string
  creatorType: 'user' | 'tmcut' | 'ai' | 'third-party'
  category: string
  tags: string[]
  thumbnailRef?: string
  previewRef?: string
  target: {
    aspectRatio?: string
    frameRate?: { numerator: number; denominator: number }
    durationRangeTicks?: { min: number; max: number }
  }
  placeholders: TemplatePlaceholder[]
  projectBlueprint: unknown
  requiredAssets: Array<{
    assetId: string
    versionRange?: string
    required: boolean
    fallback?: 'ask-user' | 'omit' | 'replace'
  }>
  compatibility: {
    minimumTMCutVersion: string
  }
  license?: AssetLicenseRecord
}
```

Do not use `unknown` in the final production schema without runtime
validation. Reuse the actual Timeline DSL and versioned schema.

### 6.3 Placeholders

A placeholder can represent:

-   Main video
-   Supporting video/B-roll
-   Image
-   Logo/brand image
-   Title/subtitle text
-   Voice-over
-   Music bed
-   SFX cue
-   Color/brand palette
-   CTA/end card

Each placeholder should define accepted media types, required/optional
status, default duration behavior, crop/fit policy, replacement rules,
and whether AI may generate a replacement. If a replacement changes
duration, use a documented fit policy: trim, speed within limits,
freeze/hold where appropriate, or extend the surrounding sequence. Never
silently distort a clip's timing in a way that breaks narration or
synchronization.

### 6.4 Applying a template

1.  Validate template schema and compatibility.
2.  Check required assets and their rights/installation state.
3.  Collect missing placeholder inputs.
4.  Create a new project or a new sequence using Core commands.
5.  Resolve placeholders to asset IDs and media metadata.
6.  Recompute timing using deterministic rules.
7.  Validate overlaps, gaps, track types, duration, and render
    capabilities.
8.  Show a preview/summary before committing if changes are extensive.
9.  Support undo/redo and project autosave.
10. Preserve the original template; edits apply to the project instance
    unless the user explicitly saves a new template version.

### 6.5 AI-generated templates

The AI should generate a **Template Plan**, not arbitrary serialized
project JSON with no validation. The pipeline:

``` text
User brief
 -> Parse goals and constraints
 -> Select target profile and template structure
 -> Generate structured Template Plan
 -> Validate schema and asset references
 -> Resolve placeholders and required assets
 -> Build project using Core commands
 -> Preview / review
 -> Save as editable project and optionally as template
```

Allow user edits before saving. Label AI-generated material and
distinguish generated media from stock/library assets. Record
provider/model metadata when useful, but never store secrets or private
prompts unnecessarily.

# PART C --- AI EDITOR

## 7. AI Editor goals

AI Editor is a conversational assistant embedded in the normal editor.
It can start from an empty project, a selected clip, an existing
timeline, or a template.

Example user requests:

-   "Create a 30-second vertical food promo from these clips."
-   "Make this feel energetic but keep the original dialogue."
-   "Add a music bed, subtle whooshes at transitions, and captions."
-   "Use the selected template but replace its placeholders with my
    media."
-   "Shorten the first section and make the ending more cinematic."
-   "Generate a cover image and an end card using my brand colors."

### 7.1 AI Editor capabilities

-   Understand project intent, media inventory, selected clips, and
    target output.
-   Analyze media metadata and optionally visual/audio content through
    approved providers.
-   Propose a complete editable timeline.
-   Suggest or generate title/caption text.
-   Find compatible licensed assets from Asset Center.
-   Generate images or other media through a configured provider when
    supported and permitted.
-   Recommend music/SFX based on mood, pace, scene transitions, and
    rights.
-   Place audio cues and music with fades, ducking, and synchronization
    rules.
-   Suggest effects, filters, transitions, and speed changes supported
    by current render capabilities.
-   Generate a Template Plan from the result.
-   Apply changes iteratively through structured edit operations.
-   Explain changes and provide a diff/preview before large destructive
    modifications.
-   Undo AI operations as a group or through normal command history.
-   Ask the user only for essential missing information; use safe
    defaults for optional details and show those assumptions.

### 7.2 AI must not be the source of truth

The AI returns structured data such as:

``` ts
interface AIEditPlan {
  schemaVersion: number
  intentSummary: string
  assumptions: string[]
  target: {
    durationTicks?: number
    aspectRatio?: string
    frameRate?: { numerator: number; denominator: number }
  }
  operations: EditOperation[]
  requiredAssets: RequiredAssetRequest[]
  generatedMediaRequests: GeneratedMediaRequest[]
  warnings: string[]
}
```

`EditOperation`, `RequiredAssetRequest`, and `GeneratedMediaRequest`
must be real validated types in the implementation, not unchecked
objects. Do not let the model set arbitrary local paths, credentials,
shell commands, or unrestricted URLs.

### 7.3 Operation pipeline

``` text
User instruction
 -> Gather allowed project context
 -> AI planning
 -> Parse structured output
 -> Schema validation
 -> Permission and cost checks
 -> Asset/provider capability resolution
 -> Dry-run and project diff
 -> User confirmation for major changes
 -> Apply through Core edit commands
 -> Update History/autosave
 -> Preview
 -> Optional render
```

-   Small reversible edits may be applied immediately if the user has
    enabled that mode.
-   Full-project generation, media generation, destructive edits, paid
    requests, and final export should have clear confirmation/settings
    controls.
-   Reject invalid plans and request a bounded repair attempt; never
    blindly apply malformed output.
-   Keep a plan trace that records operations and results without
    exposing provider secrets.
-   A provider outage must not corrupt the project.

### 7.4 Audio planning

The plan should model audio semantically:

-   `music-bed`
-   `voice-over`
-   `dialogue`
-   `ambient`
-   `foley`
-   `transition-sfx`
-   `impact-sfx`
-   `ui-sfx`

For each cue, specify target timeline range, source asset or generation
request, gain target, fade in/out, optional ducking target, and
synchronization anchor. Use the existing audio waveform/probe
capabilities where available. The renderer remains responsible for
actual mixing and export.

Music/SFX sourcing order should be configurable, for example: 1.
User-provided media. 2. Installed/licensed Asset Center resources. 3. An
authorized provider or catalog. 4. AI-generated audio through a provider
whose API and license terms have been verified. 5. Omit the cue and warn
the user if none is available.

Do not silently substitute copyrighted or unlicensed music. Generated
audio also requires review of the provider's terms and output
restrictions.

# PART D --- AUTOCUT AI

## 8. AutoCut product definition

AutoCut is a high-automation workflow, not merely a chat panel. The user
provides source media and a description; TMCut handles analysis, plan
creation, asset selection/generation, timeline construction, validation,
preview, and export orchestration.

Example input: - Source video files or a folder. - Desired outcome,
mood, audience, platform, and language. - Optional target
duration/aspect ratio/resolution. - Optional template/profile. -
Optional preferences: preserve dialogue, use subtitles, use supplied
music, allow generated images, allow generated video, maximum generation
budget.

Avoid requiring every setting up front. Provide sensible defaults and a
review screen before paid generation or final render.

### 8.1 AutoCut stages

``` text
1. Ingest
   -> Validate input media and permissions
   -> Probe duration, frame rate, dimensions, audio streams

2. Analyze
   -> Create thumbnails/keyframes/waveforms as needed
   -> Detect scenes and candidate highlights
   -> Transcribe speech when enabled and supported
   -> Analyze audio/music/dialogue
   -> Build a media inventory with timestamps

3. Interpret brief
   -> Determine narrative, pacing, target duration, aspect ratio
   -> Build an edit brief and explicit assumptions

4. Plan
   -> Select an AutoCut profile/template
   -> Create Edit Plan / Timeline DSL operations
   -> Plan title/caption/audio/SFX/transition cues
   -> Identify missing media

5. Resolve assets
   -> Prefer user assets and installed licensed resources
   -> Request approval for downloads or paid generation
   -> Generate image/video/audio only when configured and supported
   -> Track provenance, provider, task IDs, and rights metadata

6. Build
   -> Apply operations through TMCut Core
   -> Construct video/audio/text/effect tracks
   -> Validate timing, overlap, sync, missing media, and capabilities

7. Review
   -> Render a low-cost preview/proxy when feasible
   -> Show warnings, missing assets, assumptions, and timeline summary
   -> Allow edits or regenerate selected sections

8. Final render
   -> Select compatible RenderBackend
   -> Run existing FFmpeg backend initially
   -> Show progress, cancellation, errors, output location

9. Save
   -> Save editable project and output metadata
   -> Optionally save result as a reusable template
```

### 8.2 Scene and timeline analysis

Use the current FFmpeg/FFprobe pipeline where possible. Add capabilities
incrementally:

-   Metadata/probe.
-   Thumbnail and keyframe extraction.
-   Scene-boundary candidates.
-   Audio waveform and silence detection.
-   Speech-to-text/transcript alignment through an approved provider.
-   Optional semantic visual analysis.
-   Highlight candidates with evidence/timestamps.
-   Candidate selection based on narrative relevance, not just scene
    duration.

Keep expensive semantic analysis optional. Every analysis result should
reference source asset IDs and timestamp ranges so the plan can be
audited and corrected.

### 8.3 AutoCut profile

Profiles should be versioned configuration, not hidden prompt text only.
Example fields:

-   Intended format and aspect ratio.
-   Target duration range.
-   Pacing preference.
-   Hook/opening policy.
-   Story structure.
-   Caption style.
-   Music/SFX policy.
-   Transition policy.
-   Allowed effect families.
-   Dialogue-preservation policy.
-   Asset source priority.
-   Generation permissions and budget ceiling.
-   Render quality preset.
-   Safety/rights restrictions.

Example profile IDs: `shorts-fast-cut`, `product-promo`, `food-reel`,
`podcast-highlights`, `vlog-recap`. These are examples, not a
requirement to hardcode a fixed list.

### 8.4 Fully automated does not mean unbounded

AutoCut can run without constant manual timeline editing, but it must
respect: - User-selected output directory. - Approved source files. -
Generation and spending limits. - Provider availability and rate
limits. - Asset license rules. - Render capabilities. - User's choice to
preserve or replace original audio. - Confirmation settings for external
uploads, paid generation, and final export.

Do not upload local media to a third-party provider without clear
disclosure and the applicable user consent. Prefer local analysis where
feasible and show which media will leave the device.

# PART E --- AI PROVIDER HUB

## 9. Provider integration strategy

Do not hardcode provider calls inside AI Editor or AutoCut. Create a
capability-based Provider Hub with adapters.

Important distinction:

-   **LLM/model gateways** return text, structured output, tool calls,
    or supported multimodal responses.
-   **Coding/agent runtimes** may expose their own APIs or custom
    endpoints; their local CLI/configuration is not automatically a
    supported production API for embedding in TMCut.
-   **Image/audio/video generation services** often have asynchronous
    jobs, provider-specific inputs, polling, callbacks, and
    media-download steps. They need a separate adapter contract from
    chat completions.

### 9.1 Provider categories

``` ts
type ProviderCapability =
  | 'chat'
  | 'structured-output'
  | 'tool-calling'
  | 'vision'
  | 'image-generation'
  | 'speech-to-text'
  | 'text-to-speech'
  | 'audio-generation'
  | 'video-generation'
  | 'video-understanding'
```

A provider connection may support one or several capabilities. Do not
infer capabilities from a provider's name; verify them from the
provider's documented API and model metadata.

### 9.2 Adapter contracts

``` ts
interface LLMProviderAdapter {
  id: string
  listModels(): Promise<ModelDescriptor[]>
  generate(request: LLMRequest): Promise<LLMResult>
  testConnection(): Promise<ProviderHealthResult>
}

interface MediaGenerationAdapter {
  id: string
  capabilities: ProviderCapability[]
  submit(request: MediaGenerationRequest): Promise<GenerationJob>
  getJob(jobId: string): Promise<GenerationJobStatus>
  cancel?(jobId: string): Promise<void>
  retrieveResult(jobId: string): Promise<GeneratedMediaResult[]>
}
```

These are conceptual contracts. Implement separate interfaces if a
provider has materially different sync/async behavior. Validate all
request and response payloads.

### 9.3 Provider configuration

Store non-secret settings separately from credentials:

-   Provider ID and display name.
-   Adapter type and endpoint mode.
-   Base URL, if applicable.
-   Enabled capabilities.
-   Selected/default model per capability.
-   Model allowlist.
-   Timeout and retry policy.
-   Concurrency limits.
-   User-defined monthly/daily request or cost limits where supported.
-   Privacy/upload policy.
-   Last health check and error status.
-   API compatibility version.
-   Whether the provider supports cancellation, job polling, streaming,
    structured output, image inputs, and result download.

Credentials must be stored using OS-secure storage or a trusted backend
secret store. Never place API keys in source control, renderer bundles,
logs, project files, template files, or AI prompts. For a desktop-only
local mode, document that locally stored keys are still sensitive and
protect them appropriately. If using a shared backend, use server-side
provider credentials and per-user authorization/quotas.

### 9.4 Provider routing

The orchestrator should choose a provider based on: - Required
capability. - Model availability. - User preference. - Quality
requirements. - Latency. - Price/budget where known. - Privacy
constraints. - Provider health and rate limits. - Whether the task
supports structured output or asynchronous jobs.

Fallback is allowed only to another provider that supports the same
required capability and output contract. Do not silently fall back to a
paid provider or upload media to a different provider without respecting
user settings.

### 9.5 OpenRouter

Implement a dedicated adapter or a carefully configured
OpenAI-compatible adapter after checking current official docs. The
official API documents chat completions and a model catalog endpoint;
models have different capabilities, and model IDs/availability can
change.

Official references: -
https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request -
https://openrouter.ai/docs/api/api-reference/models/get-models

Requirements: - Discover models dynamically where appropriate. - Store
model IDs and capability metadata, not assumptions based on display
names. - Normalize usage, errors, rate limits, and streaming. - Respect
provider/model-specific parameters. - Test structured output and
tool-call behavior per model. - Do not assume every model supports
vision, audio, or video generation.

### 9.6 OpenCode

Treat OpenCode integration as a separate decision, not simply "call the
OpenCode app." The official docs describe provider configuration and
custom OpenAI-compatible providers. Newer OpenCode Console provider
endpoints may provide an API for connected providers, but the
integration must use the documented supported product/API and
appropriate service-account credentials.

Official references: - https://dev.opencode.ai/docs/providers -
https://dev.opencode.ai/v2/docs/console/api/providers

Implementation rules: - Do not scrape the OpenCode UI or depend on
undocumented internal endpoints. - Do not assume a local OpenCode CLI is
a stable production API for TMCut. - Support a custom compatible
endpoint only when its request/response contract is verified. - Store
endpoint URL and auth mode as configuration; store secrets securely. -
Test provider identity, model IDs, streaming, errors, and rate-limit
behavior. - Keep the adapter optional so TMCut can operate without
OpenCode installed.

### 9.7 freeLLAMAPI

Before implementing this connector, verify the exact product/site the
user intends by checking its current official API documentation. Do not
guess its base URL, authentication format, model identifiers, quota
behavior, or whether it is an aggregator or a compatible proxy.

If it exposes a documented OpenAI-compatible API: - Use a configurable
OpenAI-compatible adapter. - Keep its model catalog and limits
provider-specific. - Implement a connection test and a minimal request
test. - Document reliability, privacy, rate limits, and fallback
behavior. - Never promise "free forever"; pricing and quotas may change.

If its API is not compatible, implement a dedicated adapter only after
the request/response contract is documented and tested.

### 9.8 Seedance 2.5

Treat Seedance 2.5 as a video-generation model/service requiring a
dedicated **video-generation adapter**, not an LLM chat adapter. Before
coding, verify the exact official provider/API, model version,
availability in the user's region/account, supported input modes,
duration/resolution/aspect ratio, asynchronous job behavior, output
retrieval, pricing, and usage rights.

Do not assume a public API is available simply because a model or
feature appears in a consumer product. If there is no authorized
documented API available to the application, mark the connector
`planned/unavailable` and do not automate the consumer website, bypass
access controls, or rely on private endpoints.

### 9.9 Google Flow

Treat Google Flow as a creative video-generation product until a
supported API for the exact required workflow has been verified. Do not
assume the consumer Flow UI is itself an embeddable API.

Before implementation: - Verify official developer documentation for a
supported model/API that meets the use case. - Determine whether the
intended integration is through an official video-generation API, an
authorized partner, or no supported API. - Record capability,
account/region eligibility, rate limits, pricing, job polling, output
access, and usage terms. - If no supported integration exists, leave it
as a future connector and allow users to import output media manually. -
Do not automate browser UI or use undocumented endpoints as a substitute
for API access.

### 9.10 Provider readiness registry

Every provider connector should have a status:

-   `planned`
-   `docs-unverified`
-   `implemented`
-   `tested`
-   `production-ready`
-   `temporarily-unavailable`
-   `deprecated`

Only show a connector as available in the production settings UI after
its API contract, credential flow, model/capability mapping, error
handling, and tests are verified. A roadmap mention does not mean the
connector is implemented or that the provider exposes an API.

# PART F --- MEDIA GENERATION AND PROVENANCE

## 10. Generated media workflow

Generated images, audio, and videos must enter TMCut through the same
asset/provenance layer as imported media.

Track where applicable: - Generated media ID. - Provider and model. -
Provider job ID. - Prompt/reference metadata where privacy policy
allows. - Creation timestamp. - Output MIME type, size,
dimensions/duration, checksum. - User consent/upload mode. - Applicable
license/terms snapshot or reference. - Attribution/label requirements. -
Whether the media is temporary, project-local, or saved to Asset Center.

Do not store API secrets or unnecessary personal data in provenance
metadata. Allow users to delete generated files and associated metadata
subject to project integrity and applicable service requirements.

### 10.1 Generated video limitations

Provider output may not match the target aspect ratio, duration, frame
rate, audio format, or visual continuity. Add a normalization
pipeline: - Probe result. - Validate media type and dimensions. -
Convert or transcode only when needed and supported. - Generate
thumbnails. - Register as a media asset. - Warn about audio, frame-rate,
or resolution changes. - Preserve original generated output unless the
user opts to replace/remove it.

Generated clips should be treated as source clips inserted into the
timeline; they do not automatically replace the timeline or become an
authoritative edit plan.

### 10.2 User-provided source media

-   Ask before sending local source media to a third-party service.
-   Offer local-only analysis where feasible.
-   Explain which files, thumbnails, audio segments, or prompts will be
    transmitted.
-   Do not upload full source video if a provider can work from a
    user-approved excerpt or a locally generated low-resolution proxy.
-   Respect provider retention and privacy settings; do not claim
    deletion or zero retention unless verified.

------------------------------------------------------------------------

# PART G --- RENDERING AND EXPORT

## 11. Render architecture remains backend-independent

Keep the current FFmpeg backend operational. Add render capabilities
only behind a stable render interface and normalized render graph.

-   AI Editor and AutoCut produce plans, not FFmpeg command strings.
-   TMCut Core validates project/timeline operations.
-   Render Graph represents the desired composition.
-   The selected backend translates the graph into its execution model.
-   The backend reports progress, cancellation, warnings, and output
    metadata through normalized events.
-   Unsupported effects must be reported before export where possible.
-   Preview and final render should share semantic definitions, but
    exact pixel parity across different engines must be tested, not
    assumed.

A Rust/native backend or WebCodecs backend can be introduced later
without redesigning AI planning, templates, or asset metadata.

# PART H --- SECURITY, COST, AND PRIVACY

## 12. Guardrails

-   Treat provider responses, generated plans, asset metadata, archives,
    and downloaded media as untrusted input.
-   Validate structured output with runtime schemas.
-   Keep credentials out of renderer code, logs, projects, and prompts.
-   Use allowlisted endpoints and HTTPS; validate redirects.
-   Set request timeouts, bounded retries, cancellation, and concurrency
    limits.
-   Enforce maximum source file size, generated duration, output
    resolution, and job budget.
-   Show expected or estimated cost when the provider supplies reliable
    pricing data; label estimates as estimates.
-   Require confirmation before paid generation if the user has not
    explicitly enabled a budget policy.
-   Avoid silent provider fallback that changes cost or privacy.
-   Keep a local job history with sanitized errors and clear retry
    actions.
-   Do not execute generated scripts, downloaded plugin code, or
    arbitrary shell commands.
-   Do not allow AI-generated paths to escape the permitted
    project/output directories.
-   Ask for consent before sending local media to external services.
-   Provide a way to disable AI/provider features and continue manual
    editing.
-   Follow provider terms, user rights, and applicable privacy
    obligations.

# PART I --- UX AND STATE MODEL

## 13. AI Editor UI

Recommended layout: - Chat/task panel docked beside the preview or in a
resizable panel. - Current project context and selected media summary. -
Prompt/input with optional attachments and explicit upload disclosure. -
Plan summary and operation list. - Required asset and generated-media
checklist. - Provider/model selection or "Auto" policy. - Estimated

applied changes go through Core commands and the existing project

## 14. AutoCut UI

A compact wizard: 1. Choose input video(s)/folder. 2. Describe desired
output. 3. Choose target profile or leave Auto. 4. Set optional
duration, ratio, language, music/dialogue policy. 5. Set whether AI may
generate missing media and the allowed budget. 6. Review privacy/upload
and generation summary. 7. Start job. 8. View pipeline progress and
warnings. 9. Preview/edit or regenerate selected parts. 10. Export and
save the editable project.

Show clear stages such as `ingesting`, `analyzing`, `planning`,
`resolving-assets`, `generating-media`, `building-timeline`,
`previewing`, `rendering`, `completed`, `failed`, and `cancelled`.

Persist job state sufficiently to recover after an app restart where
practical. Cancellation must stop cancellable provider jobs and local
tasks; clearly mark any remote job that cannot be cancelled.

## 29. Long-term design principle

TMCut should not become a collection of provider-specific scripts. It
should be a video-editing platform with:

-   **TMCut Core** as the source of truth for editable projects.
-   **Asset Center** as a rights-aware on-demand resource catalog.
-   **Template Studio** as the reusable project/template system.
-   **AI Editor** as a validated conversational editing interface.
-   **AutoCut AI** as a job-based automation pipeline.
-   **AI Provider Hub** as the capability-aware integration layer.
-   **Preview and Render Engines** as separate execution systems.

This allows TMCut to use FFmpeg now, add other render backends later,
change AI providers without redesigning the editor, and progressively
evolve from manual editing to template-driven and AI-assisted video
creation.
